# ReinforceBean — 이 트래픽에 이 서버면 되는가

**넣는 것**: 트래픽(rps · 시간대별 곡선 · 작업 구성) + **서버 설정 후보 여러 벌**(스레드 · 커넥션 · 큐 · DB 시간)
**나오는 것**: ① 어디가 먼저 터지는가 ② 각 설정이 **몇 rps에서** 터지는가 ③ 어느 설정이 나은가
④ 그 설정에 맞는 EC2/RDS와 월 비용

```
트래픽 평균 150rps (한국형 곡선 → 피크 230)     →  DB 커넥션이 먼저 막힌다 (ρ 0.86)
작업 조회 90% 20ms + 검색 10% 150ms            →  T50·C10 은 316rps에서 무너지고, C20 은 버틴다
                                               →  커넥션 8 · 스레드 16 이면 p95 120ms · 실패 0%
                                               →  t4g.small + db.t4g.xlarge = $312/월
```

운영 중인 서버에서는 커넥션 풀을 10에서 3으로 줄여보는 실험을 할 수 없다. 여기서는 할 수 있다.
그리고 그 예측이 맞다는 것을 **실제 서버에 부하를 걸어, 보정에 쓰지 않은 조건에서** 확인한다.

## 실행

```bash
node validation/fetch_public.js     # 공개 실측 데이터 받기 (최초 1회)
python -m http.server 8000          # → http://localhost:8000
```

데이터 없이 `index.html` 만 열어도 시뮬레이션은 전부 동작한다.
**처음이라면 오른쪽 위 「예제로 전체 흐름 실행」 버튼 하나로 끝까지 돌아간다** (약 35초).

## 화면 — 한 페이지, 스크롤 없음

```
┌ ①조건 ②병목 ③설정 비교 ④최소 자원 ⑤개선안 ⑥보정 ⑦인프라 ⑧저장 ─────────┐
├────────┬────────────────────────────┬──────────────────────────────┤
│ A 입력  │ D9 후보 비교 (표)            │ D 판단 근거 — 전부 펼침         │
│ 트래픽  │  후보 × 설정열 | 결과열       │  D1 병목 · 지표               │
│ 작업    ├────────────────────────────┤  D4 최소 자원                 │
│ 서버 설정│ B 진단                      │  D6 개선안 비교                │
│ A4 후보 │  스레드│커넥션│대기 큐│요청 수지│  D7 실측 보정                 │
│        │  지연 분해 (전폭 띠)          │  D5 인프라 · D8 저장           │
│        ├──────────────┬─────────────┤                              │
│        │ C 타임라인    │ 성능 곡선     │                              │
└────────┴──────────────┴─────────────┴──────────────────────────────┘
  [일시정지][처음으로] 시뮬 22.3s ━━●━━ 시나리오 위치   표시 구간
```

**자원마다 성질이 다르므로 그림도 다르게 쓴다.**

| 항목 | 성질 | 시각화 |
|---|---|---|
| 스레드 | 정해진 슬롯을 몇 개 쓰는가 | **도트 매트릭스** — 칸 하나가 슬롯 하나 |
| 커넥션 | 같은 슬롯 문제, 다만 개수가 적다 | **도트 매트릭스** (칸이 크다) |
| 대기 큐 | 지금 값보다 *쌓이고 있는가* | **스파크라인** (면적) |
| 요청 수지 | 유입이 어디로 갈라졌는가 | **분기 흐름** (생키) |
| 지연 분해 | 한 건의 시간이 어디서 나갔나 | **100% 띠** 한 줄 |

- **D9 후보 비교 표가 화면의 주인공.** 첫 행이 기준, 나머지 행에 기준 대비 증감이 붙고 나쁜 칸일수록 붉다.
- **D1~D8은 접지 않는다.** 항상 펼쳐져 있고 결과만 각자 작은 스크롤을 쓴다.
- **색은 회색 농담 + 파랑 1색.** 빨강은 한계를 넘었을 때만.
- **성능 곡선**: 후보별 p95 vs 유입. 세로 점선이 과부하 시작점, 네모가 피크에서의 위치.

## 1. 어디가 먼저 막히는가

### 같은 100rps가 같은 100rps가 아니다 (A3 작업 구성)

| 구성 (둘 다 100 rps) | 실효 DB 시간 | 커넥션 10개의 한계 | 시뮬 p95 |
|---|---|---|---|
| 조회 90% (20ms) + 검색 10% (150ms) | 33 ms | **303 rps** | 104 ms |
| 조회 50% + 검색 50% | 85 ms | **118 rps** | 452 ms |

요청 비율로는 10%인 검색이 DB 시간의 45%를 먹는다. 그래서 **작업별 p95를 따로 본다.**

```
전체 p95 196ms   ← 대시보드에 뜨는 숫자
  ├ 상품 조회 100ms
  └ 복잡 검색 698ms   ← 사용자의 10%가 실제로 겪는 것
```

### 장애 패턴 6종

| 시나리오 | 무슨 일이 | 흔한 오해 | 판정기가 짚는 것 |
|---|---|---|---|
| 스파이크 / 점증 | ρ→1 에서 대기시간이 비선형으로 폭발 | "부하 2배면 응답도 2배" | 임계 접근 → 커넥션 병목 |
| 슬로우 쿼리 | DB 시간 5배, 유입은 그대로 | "앱 CPU는 멀쩡한데?" | DB 시간 상승 + 커넥션 100% |
| 재시도 폭풍 | 유입이 정상으로 돌아와도 처리량 0 | "스파이크 끝났는데 왜?" | 재시도 비율 + **낭비** |
| Thundering herd | 재시작 직후 몰린 요청으로 큐 즉시 포화 | "재시작하면 낫겠지" | 거절 폭주 → 램프업 필요 |
| 큐 지연 축적 | 에러 0%인데 p95가 수 초 | "에러율 0이니 정상" | 실패 낮음 + p95 높음 + 큐 적체 |
| 작업 구성 편중 | 유입 그대로인데 무거운 작업만 늘어 포화 | "트래픽 안 늘었는데?" | 소수 작업이 DB 시간 대부분 점유 |

**낭비(고아 요청)가 핵심이다.** 클라이언트가 타임아웃으로 포기해도, 취소 전파가 없으면 서버는 그 요청을 끝까지 처리한다.
이 낭비가 용량을 갉아먹어 재시도 폭풍이 스스로 유지된다. 「취소 전파」를 켜면 ③ 요청 수지에서 회복이 바로 보인다.

## 2. 같은 트래픽에서 어느 설정이 나은가 (A4 → D9)

서버 설정 한 벌(스레드·커넥션·큐·DB 시간·α·γ)을 **후보**로 저장해 둔다. 여러 벌을 쌓아 놓고,
**같은 작업 구성·같은 트래픽**에서 rps를 올려가며 각 후보가 몇 rps에서 무너지는지를 나란히 놓는다.

```
A4 「이 설정을 후보로」 → 슬라이더를 바꿔 다시 추가 → … → D9 「같은 트래픽에서 비교」
```

실행 예 (피크 250rps, 목표 p95 300ms, 단일 30ms 작업, 보정 전 α=0):

| 후보 | 설정 | 과부하 시작 | 피크 p95 | 인스턴스 (추정) | $/월 |
|---|---|---|---|---|---|
| 기준 | T50·C10·Q100 | **316 rps** | 104 ms | t4g.small + db.t4g.2xlarge | $609 |
| 커넥션 2배 | T50·C20·Q100 | 구간 밖 (>450) | 104 ms | t4g.small + db.m6g.4xlarge | $1304 |
| 스레드 2배 | T100·C10·Q100 | **311 rps** | 108 ms | t4g.small + db.t4g.2xlarge | $609 |

- **「과부하 시작」이 이 표의 핵심이다** — p95가 목표를 넘거나 실패율이 허용치를 넘는 첫 rps.
  구간 안에서 선형보간해 "몇 rps까지 버티는 서버인가"를 한 숫자로 만든다.
- 스레드만 2배로 늘린 후보는 과부하 시작점이 316 → 311 rps로 오히려 제자리다.
  화면이 이 사실을 직접 문장으로 짚는다: *병목이 DB라 앞단을 넓혀도 소용없다.*
- 각 후보에 **필요한 EC2/RDS와 월 비용**이 붙는다 — "커넥션을 2배로 하면 DB를 2배 사야 한다"가 돈으로 보인다.
- 곡선은 **C2 차트에 후보별로 겹쳐** 그려진다. 가로 점선이 목표 p95, 세로 점선이 각 후보의 과부하 시작점이다.
- 후보 목록은 **JSON으로 저장·불러오기**가 된다 (작업 구성·SLO도 함께 담긴다). 설정만 담고 결과는 항상 다시 계산한다.
- 「슬라이더에 적용」을 누르면 그 후보가 실제로 도는 모습을 **C 타임라인**에서 볼 수 있다.

> 보정 전(α=0)에는 커넥션 경합이 없다고 보므로 과부하 시작점이 실제보다 낙관적으로 나온다.
> 화면도 그렇게 경고한다 — ⑥ 실측 보정을 거친 뒤의 표라야 믿을 수 있다.

## 3. 그래서 뭘 고쳐야 하는가 (D6)

같은 피크 · 같은 작업 구성에서 대안을 각각 돌려 **성능 · 비용 · 다음 병목**을 나란히 놓는다.
(250rps, 조회 90 / 검색 10, 커넥션 10, α=0.8)

| 개선안 | p95 | 실패 | 월 비용 |
|---|---|---|---|
| 현재 구성 | 1056 ms | 34.7% | $609 |
| 커넥션 10 → 20 (DB 그대로) | 708 ms | 3.0% | $609 |
| 스레드 50 → 100 | 1488 ms | 36.2% | $609 |
| **DB 인스턴스 증설 (코어 2배 → 커넥션 20)** | **208 ms** | **0%** | $1304 |
| **DB 시간 −50% (쿼리 개선 가정)** | **120 ms** | **0%** | $609 |

- **커넥션만 2배(708ms)와 DB 증설(208ms)은 다르다.** 커넥션 수는 같은데 왜? DB 코어는 그대로인데 동시 쿼리만
  2배로 밀어넣으면 경합이 커져 **쿼리 자체가 느려지기 때문**이다(α 0.8→1.6). 여기가 "돈을 써야만 하는" 구간이다.
- **스레드를 늘리면 오히려 나빠진다.** 병목이 DB인데 앞단만 넓히면 대기만 늘어난다.
- 모든 안에 **「다음 병목」**이 붙는다. 자원을 늘리면 병목은 사라지지 않고 옮겨간다.

> α = 0 이면 「커넥션 2배」와 「DB 증설」이 모델상 구분되지 않는다. ⑥ 보정으로 α를 실측해야 두 안이 갈린다.

## 4. 이 예측을 왜 믿는가 (`validation/` + D7)

시뮬레이터와 **같은 구조**의 실제 서버(큐 → 스레드 → SQLite 커넥션 풀)에 포아송 부하를 건다. 의존성 없음.

```bash
cd validation
node server.js                        # THREADS=50 CONNS=10 QUEUE=100 DB_MS=30
node load.js --out result.csv         # 단계별 p50/p95/p99/실패율 → CSV
node compare.js result.csv --alpha 0.39 --fit 50,250,400 --holdout 100,150,200,300,330,360
```

### 발견 ① — 단독 벤치마크는 부하 아래서 거짓말을 한다

```
[calibrate] 실효 단독 34.4ms  |  10개 동시 70.0ms → 실질 용량 ≈ 143rps
[calibrate] ⇒ α = 1.03
```

관리자가 아는 "쿼리 34ms"로 용량을 잡으면 **2배 과대평가**한다. 서버가 시작할 때 이 α를 직접 재서 출력한다.

### 발견 ② — 감속은 비선형이다

250rps까지 p95가 129ms로 **평평하다가** 300rps에서 654ms로 **절벽처럼** 떨어진다. 그래서 지수 γ를 둔다.

```
실효 DB 시간 = DB시간 × dbScale × (1 + α × (사용 중 커넥션 / 커넥션 수)^γ)
```

| | 뜻 | 어떻게 아나 |
|---|---|---|
| `dbScale` | 한산할 때 실제 DB 시간 배율 | 낮은 rps 실측 |
| `α` | 커넥션이 **꽉 찼을 때** 몇 배 느려지나 | `server.js` 가 직접 측정해서 출력 |
| `γ` | **언제부터** 느려지기 시작하나 | 무릎 직전 rps 실측 |

`(k/c)^γ` 형태라서 k=c 일 때 배율이 정확히 `(1+α)` 가 된다. 즉 서버가 직접 잰 α를 그대로 넣을 수 있다.

| 모델 | 250rps (실측 129ms) | 300rps (실측 654ms) | 전 구간 오차 |
|---|---|---|---|
| 경합 무시 (α=0) | 104 ms | 292 ms ← 무릎을 놓침 | 19% |
| 선형 γ=1 | 748 ms ← 무릎이 너무 이름 | 724 ms | 61% |
| **비선형, α 실측값** | **204 ms** | **648 ms** | **9%** |

### 발견 ③ — holdout에서 맞아야 증거가 된다

보정에 쓴 점에서 잘 맞는 건 당연하다. **쓰지 않은 rps**에서 확인한다.

```
[보정] 사용 rps: 50, 250, 400   (자동 선택: 한산 · 무릎 직전 · 포화)
[검증] 보정에 쓰지 않은 rps
 rps | 실측 p95 | 보정 전 오차 | 보정 후 오차
 200 |     115 |         23% |         13%
 300 |     654 |         74% |         11%   ← 168ms → 584ms
 360 |     746 |         29% |         16%
 평균 |         |     　  27% |          9%
```

**300rps가 핵심이다.** 보정 전에는 "아직 여유롭다"(168ms)고 하던 지점이 보정 후 "이미 무너진다"(584ms)로 바뀐다.
용량 계획에서 가장 비싸게 틀리는 지점이 정확히 여기다.

### 안 되는 경우는 안 된다고 말한다

- 파라미터가 셋이니 보정 점도 **한산 · 무릎 직전 · 포화** 셋이 다 필요하다. 「자동 선택」이 CSV에서 골라준다.
- 셋을 한 격자에서 동시에 맞추면 `dbScale` 과 `γ` 가 서로를 상쇄한다("느린 쿼리 + 늦은 감속" = "빠른 쿼리 + 이른 감속").
  그래서 **각각을 그것이 드러나는 구간에서 따로** 잰다 → 보정 25초→2초, holdout 오차 30%→4~12%.
- 보정 구간이 전부 한산하면 α·γ 는 이 데이터로 결정되지 않는다. 그럴 때 D7은 **"식별 불가"** 라고 경고한다.

## 5. 그래서 어떤 인스턴스인가 (D4 → D5)

Erlang C로 용량 부족 조합을 1차 컷 → 남은 조합을 헤드리스 시뮬로 확정 → 최소 비용 (D4).
그 조합의 필요 vCPU·메모리를 추정해 최소 EC2/RDS를 고르고, **근거 사슬 7단계**를 보여준다 (D5).

```
①  피크 트래픽   230 rps   ← 실측 곡선의 피크/평균 1.53배 × 평균 150rps
②  병목 자원     DB 커넥션  ← 이론 ρ: DB 0.86 vs 스레드 0.50
③  필요 커넥션   8개        ← Little's Law: 230/s × 30ms = 6.9 + 변동 여유
④  필요 스레드   16개       ← 더 늘려도 커넥션이 8개뿐이라 무의미
⑤  시뮬 검증     p95 120ms · 실패 0%
⑥  DB vCPU      3.4코어    ← 8커넥션 × 쿼리 CPU 0.3 ÷ 목표 이용률 0.7
⑦  앱 vCPU      1.7코어    ← 앱은 대부분 I/O 대기
────────────────────────────────────
    t4g.small ($15/월) + db.t4g.xlarge ($296/월) = $312/월
```

**비용은 DB가 결정한다.** 스레드는 거의 공짜고, 커넥션을 늘리려면 DB 코어를 사야 한다.

> **어디까지가 추정인가.** 인스턴스 추천은 로컬 실험으로 보정한 모델의 **추정값**이며, 해당 EC2/RDS에서
> 직접 측정한 값이 아니다. CPU 세대 · EBS/네트워크 · IOPS · Multi-AZ 미고려. 보정값도 **측정에 쓴 그 기계**의 값이다.
> 화면과 리포트 모두에 이 사실을 함께 표시한다.

## 공개 실측 데이터 (`data/`)

절대 요청량이 아니라 **트래픽 모양**을 쓰고, 사용자가 정한 평균 유입으로 스케일해 재생한다.

| 데이터셋 | 종류 | 값 | 쓰임 |
|---|---|---|---|
| 위키백과(영문) 하루 / 일주일 | traffic | 피크/평균 1.17 / 1.30배 | 글로벌 서비스는 고르게 분산 |
| 한국어 위키백과 하루 | traffic | **1.53배** | 단일 시간대 서비스는 피크가 뾰족 |
| TechEmpower DB R22 | latency | 무릎 82k rps | 무릎이 실재한다는 외부 증거 |
| AWS EC2 / RDS PG (서울) | pricing | 69종 / 54종 | D5 카탈로그 |

**① 트래픽 모양이 곧 용량 계획이다.** 같은 평균 150rps라도 한국형이면 피크 230, 글로벌이면 175rps다.
**② 무릎은 실재한다.** TechEmpower R22 `db` 테스트(537개 프레임워크 중앙값): 동시성 128→512에서
처리량은 +3%인데 지연은 4.7배. 우리 모델이 ρ→1에서 예측하는 모양 그대로다.
**③ 가격은 실데이터라야 답이 바뀐다.** 하드코딩 추정치로는 x86 조합($374/월)이 나오지만, 서울 실가격을 넣으면
Graviton 조합(**$312/월**)이 최적이 된다.

> 품질 원칙: 신뢰할 수 없는 데이터는 넣지 않는다. `the-benchmarker/web-frameworks` 는 결측이 많고
> 백분위가 Little's Law 검산과 맞지 않아 제외했다.

## 이론적 근거

대기행렬 이론(M/M/c). ρ = 도착률 ÷ (서버 수 × 처리율)이 1에 가까워질수록 대기시간이 비선형으로 폭발한다.
작업 구성이 켜지면 실효 서비스 시간은 비율 가중평균 `E[S] = Σ share_i · S_i` 를 쓴다.
부하 의존 서비스 시간은 자기참조적이므로(느려지면 더 붐비고, 더 붐비면 더 느려진다)
`S(ρ) = S₀·(1 + α·ρ^γ)` 를 **고정점 반복**으로 푼다. γ 때문에 이 고정점은 낮은 부하에선 거의 S₀ 에
머물다가 ρ→1 에서 급격히 커진다 — M/M/c 보다 **날카로운 무릎**이고, 실측이 정확히 그 모양이었다.

키워드: `M/M/c`, `Erlang C`, `Little's Law`, `load-dependent service time`, `metastable failure`,
`retry storm`, `capacity planning`, `peak-to-mean ratio`, `holdout validation`, `identifiability`

### 요청의 생애

```
spawn(작업 종류 추첨) → queued → waitconn → db(종류별 시간 × 혼잡도) → cpu → done
        ↑                 ↘ rejected (큐 포화)  ─┐
        │                 ↘ 클라이언트 타임아웃 ──┼→ (확률) 재시도로 다시 유입
        │                      ↳ 취소 전파 없으면 서버는 계속 처리 → wasted (낭비)
```

## 분업 — 2파트 동시 작업

프로그램을 두 질문으로 자르면 두 사람이 서로를 기다리지 않는다.

| | **파트 1 · 진단** | **파트 2 · 판단** |
|---|---|---|
| 답하는 질문 | 이 설정에 이 트래픽 → **어디가 먼저 터지나** | 그래서 **뭘 얼마나 사면 되나** |
| 화면 | A 입력 · B 진단 · C 타임라인 · D1 D2 D3 | D4 D5 D6 D7 D8 |
| 코드 | `engine.js` (구획 1~5) | `advisor.js` (구획 6~7c) |
| 그 밖 | — | `validation/` 실측 서버 · 부하기 · 보정 |
| 성공 기준 | 장애 6종이 화면에서 서로 구분되어 보인다 | 추천한 설정/인스턴스가 실측 SLO를 만족한다 |

### 접점은 함수 하나

```js
runHeadless({ threads, conns, queueCap, dbTimeMs, alpha, gamma, mix, rps, sec })
  → { p50, p95, p99, failRate, thU, coU, brk:{q,wc,db,cpu}, out, wasted, nextBottleneck }
```

파트 2는 **이 함수만 호출한다.** 파트 1은 반환 모양만 지키면 엔진 내부를 마음대로 바꿔도 된다.
파트 2는 파트 1이 끝나기 전에도 고정값을 뱉는 스텁으로 개발을 시작할 수 있고,
파트 1은 D 패널이 어떻게 생겼는지 몰라도 된다.

### 파일 분리 — 완료

1961줄짜리 `index.html` 하나를 둘이 동시에 고치면 매번 같은 줄에서 부딪힌다.
스크립트를 `engine.js` / `advisor.js` / `app.js` 로 뗐다(위 「코드 구조」 참고).
평소 작업에서 **두 사람이 같은 파일을 건드릴 일은 `app.js` 와 `index.html` 마크업뿐**이고,
그 둘은 거의 바뀌지 않는다. 바꿔야 하면 서로에게 알린다.
