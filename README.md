# ReinforceBean

**이 트래픽에 어느 EC2 인스턴스면 충분한가**를 브라우저에서 부하 테스트로 비교해 보는 시뮬레이터.

---

## 1. 무엇을 하나

인스턴스를 실제로 띄워 부하를 걸어보지 않으면 "t3.medium 으로 될까, c6i.xlarge 가 필요할까"를 알 수 없다.
이 도구는 **여러 인스턴스에 같은 트래픽을 동시에 먹여** 그 차이를 실시간으로 보여준다.

| 넣는 것 | 예 |
|---|---|
| 트래픽 | 250 rps · 스파이크 · 슬로우 쿼리 · 실제 위키백과 곡선 |
| 서버 설정 (전 인스턴스 공통) | 스레드 50, DB 커넥션 20, 대기 큐 100, DB 30ms, 요청당 CPU 8ms |
| 비교할 인스턴스 | t3.medium · c6i.xlarge · c6i.2xlarge (최대 4대) |

| 나오는 것 | 예 |
|---|---|
| 어디가 먼저 막히나 | CPU 포화 — vCPU 2개 부족 (코어 100%, 요청 42건이 CPU 대기) |
| 인스턴스별 실시간 차이 | t3.medium CPU 100% / p95 652ms / 실패 30% · c6i.xlarge CPU 75% / p95 112ms / 실패 0% |
| 결론 | 이 트래픽에 충분한 최소 인스턴스 **c6i.xlarge** ($140/월) |

### 인스턴스가 서버에 주는 영향을 무엇으로 보나

인스턴스마다 다른 것은 **두 개뿐**이고, 나머지 설정·트래픽·DB 조건은 전부 같게 둔다.
그래야 선이 갈라지는 지점이 곧 "인스턴스 차이"가 된다.

| 사양 | 서버에 미치는 영향 |
|---|---|
| **vCPU** | CPU 슬롯 개수. `유입 × 요청당 CPU 시간`이 코어 수를 넘으면 DB 를 끝낸 요청이 CPU 앞에 줄을 선다 |
| **메모리** | 띄울 수 있는 스레드 상한 (`(GB × 60%) ÷ 8MB`). 설정이 아무리 커도 메모리가 없으면 못 띄운다 |
| *(t 계열)* | 버스터블 기준 이용률. 이 선 위로 오래 있으면 크레딧이 떨어져 스로틀된다 — 차트에 점선으로 표시 |

### 왜 예측을 믿을 수 있나

`validation/` 에 시뮬레이터와 **같은 구조로 만든 실제 서버**(대기 큐 → 스레드 → SQLite 커넥션 풀)가 있다.
여기에 진짜 부하를 걸어 나온 실측값 중 **일부 rps 로만** 모델을 맞추고, **맞추는 데 쓰지 않은 rps** 에서
예측이 맞는지 확인한다 (holdout 평균 오차 약 30% → 12%). 화면 오른쪽 아래 **「실측으로 보정 · 검증」** 버튼.

## 2. 실행 방법

### 가장 빠른 방법 — 그냥 열기

`index.html` 을 더블클릭하면 시뮬레이션과 인스턴스 비교는 전부 동작한다.
(단, 실가격 카탈로그와 공개 트래픽 곡선은 브라우저 보안 정책 때문에 못 읽어 내장값을 쓴다)

### 권장 — 로컬 서버로 열기

```bash
python -m http.server 8000        # 또는: npx serve
# → 브라우저에서 http://localhost:8000
```

이러면 `data/` 의 서울 리전 EC2 실가격(69종)과 실제 트래픽 곡선까지 전부 쓴다.

### 공개 데이터 새로 받기 (선택)

```bash
node validation/fetch_public.js            # 전부 (Node 22+)
node validation/fetch_public.js --list     # 받을 수 있는 목록
```

받는 것: 위키백과 트래픽 곡선, TechEmpower 벤치마크, AWS 서울 리전 EC2/RDS 가격.

### 실제 서버로 검증하기 (선택)

```bash
node validation/server.js                  # 스레드 50 · 커넥션 10 · 큐 100 · DB 30ms · 포트 8080
node validation/load.js --out result.csv   # 다른 터미널에서 부하 → CSV
```

만들어진 `result.csv` 는 화면의 **「CSV」** 버튼으로 불러온다.
보정은 **이 서버 설정(스레드 50 · 커넥션 10 · 큐 100 · 타임아웃 3s · DB 30ms)** 을 기준으로 맞춘다 —
직접 잰 CSV 도 같은 설정에서 재야 의미가 있다.

## 3. 화면

한 페이지에 들어가고 스크롤이 없다.

```
┌ 목표 p95 · 실패 허용치 │ 일시정지 · 처음으로 ─────────────────────────────┐
├──────────┬───────────────────┬──────────────────┬─────────────────────┤
│ 왼쪽      │ 설정 시나리오        │ 인스턴스 비교       │ 오른쪽               │
│ 입력      │  후보 설정 · 미리보기 │  지금 상태 · 판정   │  병목 판정 + 지표      │
│          │  (가운데 왼쪽 반)     │  (가운데 오른쪽 반) │                      │
│ 부하      ├───────────────────┴──────────────────┤  추천                 │
│ 서버 설정  │ 가운데 — 요청 흐름                       │   c6i.xlarge $140/월  │
│ 인스턴스   │   유입▶큐▶스레드▶커넥션▶vCPU▶완료        │                      │
│          │   (칸마다 최근 30초 추세 그래프)           │  모델 보정            │
│          ├──────────────────────────────────────┤                      │
│          │ 아래 — 인스턴스 실시간 비교               │                      │
│          │   CPU 이용률 / p95 / 처리량             │                      │
└──────────┴──────────────────────────────────────┴─────────────────────┘
```

가운데 세로 축이 곧 판단 순서다. **무엇으로 바꿔 볼까 / 지금 어떤가(리스트 좌·우) → 어디서 막히나(흐름) → 시간에 따라 버티나(차트)**.
고르는 자리가 맨 위에 오고, 그 아래로 「왜 그런가」가 두 단계로 붙는다.
오른쪽에는 결론에 필요한 것만 남긴다 — 병목 판정, 추천, 그 추천을 믿을 근거(모델 보정).

### 가운데 — 요청 흐름 (자원 대시보드가 아니라 **요청이 지나가는 길**)

자원을 칸칸이 늘어놓는 대신 요청 한 줄기가 흐르는 경로를 그린다.
그래서 "어디가 막혔나"를 지표를 읽어 추론할 필요 없이 띠가 얇아지는 자리로 바로 본다.

| 무엇 | 어떻게 읽나 |
|---|---|
| **가로 본류** | 그 구간을 실제로 통과한 **초당 건수**가 곧 띠 두께. 얇아지는 곳이 막히는 곳 |
| **노드 4개** | 길목의 자원 — ① 대기 큐 ② 스레드 ③ DB 커넥션 ④ vCPU. 막대 채움 = 이용률, `대기 n` = 그 앞에 선 건수 |
| **칸 안 추세선** | 그 자원의 최근 30초 이용률. 세로축은 0~100% 고정이라 칸끼리 바로 견준다. t 계열의 **버스터블 지속선**은 점선 |
| **제목 옆 ▲▼** | 직전 5초 대비 이용률 변화(%p). 지금 값이 같아도 **오르는 중인지**가 다르다 |
| **아래로 빠지는 띠** | 흐름 밖으로 나간 요청 — 큐 포화 **거절**, 끝냈지만 버려진 **낭비** |
| **점선 세로** | 클라이언트가 **포기**한 지점. 본류는 줄지 않는다 — 서버는 끝까지 처리한다 |
| **점선 가로(맨 아래)** | **재시도**가 유입으로 되돌아오는 되먹임. 재시도 폭풍이 스스로 유지되는 경로 |

칸 안의 추세 그래프가 이 화면의 본문이라 칸을 크게 쓴다. p95·병목·ρ 같은 한 줄짜리 요약은 맨 윗줄에 둔다.

**「낭비」가 숨은 주인공이다.** 클라이언트가 타임아웃으로 포기해도(점선) 서버는 그 요청을 끝까지 처리하고,
그 결과가 오른쪽 끝에서 「낭비」로 떨어진다. 이 낭비가 용량을 갉아먹어 재시도 폭풍이 스스로 유지된다.

### 맨 위 — 리스트 두 장 (좌우 반반)

이 화면에서 실제로 고르는 자리다. **왼쪽은 「무엇으로 바꿔 볼까」(설정 후보), 오른쪽은 「지금 어떤가」(인스턴스).**
바꿀 후보와 그 결과를 같은 화면에서 보려고 탭이 아니라 좌우로 나눠 둔다.

왼쪽은 **한 행이 후보 하나**인 넓은 표(설정과 결과가 한 줄에), 오른쪽은 반쪽 폭이라 **두 줄짜리 행**
(윗줄 = 판정에 쓰는 결과, 아랫줄 = 그 결과가 나온 조건)을 쓴다.

#### ① 인스턴스 비교 (오른쪽 반)

행 하나가 인스턴스 한 대. **지금 값만 늘어놓지 않고 세 가지를 같이 둔다.**

| 값 | 왜 있나 |
|---|---|
| CPU · 스레드 · 커넥션 (아랫줄) | 어느 자원이 먼저 차는지 — 숫자 옆 짧은 막대가 곧 이용률 |
| **여유** | 이론 최대 rps 대비 지금 유입(ρ). 여유가 없으면 지금 통과해도 곧 깨진다 |
| **$/100rps** | $/월 만으로는 못 고른다. **실제로 처리한** 100rps 당 월 비용 — 싸도 못 처리하면 비싼 것이다 |
| 배지 | `미달`(목표 밖) · `버스트`(버스터블 기준선 초과 — 크레딧 떨어지면 스로틀) |

여기는 **「지금」만** 본다. 시간에 따른 변화는 바로 아래 실시간 비교 차트가 맡는다.

행을 누르면 위 흐름도가 그 인스턴스로 바뀐다.

#### ② 설정 시나리오 (왼쪽 반)

한 행이 후보 하나. 아래 「설정 시나리오」 절 참고.

### 아래 — 실시간 비교 차트

세로 3단, 가로는 시간(초). **선은 기본이 검정이고, 리스트에서 고른 인스턴스만 색으로 굵게 나온다.**
시계열은 전부 여기로 모은다 — 위 리스트는 지금 값만, 변화는 이 차트에서.

| 단 | 읽는 법 |
|---|---|
| **CPU 이용률** | 인스턴스별 코어 점유. 점선은 버스터블의 지속 가능 기준선 |
| **p95 응답** | 빨간 점선이 목표 p95 — 이 선을 넘는 순간이 그 인스턴스의 한계 |
| **처리량** | 회색 점선이 유입(공통). 색선이 유입을 못 따라가면 그 인스턴스는 이미 포화 |

세로 점선은 시나리오 단계(스파이크 시작, 피크 등). 차트 위에 마우스를 올리면 그 시점의 전 인스턴스 값이 뜬다.

### 설정 시나리오 — 표로 저장해 두고, 돌리기 전에 미리 본다

가운데 **왼쪽 반** (왼쪽 패널의 「＋ 지금 설정을 시나리오로 저장」으로도 바로 담긴다).
슬라이더 값 한 벌(유입·스레드·커넥션·큐·DB·CPU·타임아웃·재시도)과 트래픽 시나리오를 한 행으로 저장한다.
브라우저에 남으므로(localStorage) 다음에 열어도 그대로 있다.

```
후보 · 트래픽        유입  스레드 커넥션  큐   DB   CPU  타임아웃 재시도 │ 예상 p95      처리량    실패   병목  판정
▸ 기준 (지금 설정)  270rps   50     20   100  30ms  8ms  3000ms   —   │ 592 ms       249 rps  7.4 %  vCPU  미달
커넥션 10 — 풀이…   250rps   50     10   100  30ms  8ms  3000ms   —   │ 576 ms  -3%  249 rps  2.0 %  vCPU  미달
큐 400 · 타임아웃…  360rps   50     20   400  30ms  8ms 10000ms   —   │1796 ms +203% 250 rps 27.7 %  vCPU  미달
```

**모든 셀이 인셀 차트다.** 셀이 칠해진 길이가 곧 그 값의 크기라, 숫자를 읽기 전에 크기가 먼저 보인다.

| 자리 | 뜻 |
|---|---|
| **▸ 기준 (지금 설정)** (첫 행) | 지금 슬라이더 값. 아래 행들이 이것과 견준다 |
| 설정 셀 (유입 ~ 재시도) | 막대 눈금은 **보이는 후보들 중 최댓값** — 후보끼리 길이로 바로 견줄 수 있다 (엑셀 데이터 막대와 같은 방식). 기준과 **다른 값은 진하게** 칠해져 무엇만 바꾼 행인지 한눈에 보인다 |
| 결과 셀 (예상 p95 · 처리량 · 실패) | 막대 눈금은 **목표치** — 목표를 넘으면 빨갛게 찬다. 옆의 `-3%` `+203%` 는 **기준 대비 증감률**(좋아지면 파랑, 나빠지면 빨강) |
| **병목 · 판정** | 그 설정에서 무엇이 먼저 막히는지, 목표를 `만족`하는지 `미달`인지 |
| **전체 / 만족 / 미달** | 판정으로 거르는 필터 |
| **적용** | 그 설정을 실제로 불러와 슬라이더·트래픽 시나리오까지 바꾸고 재생을 처음부터 |

미리보기는 그 설정으로 **헤드리스 20초(워밍업 6초)를 따로 돌린 예측**이다.
재생 중인 화면은 건드리지 않으므로, 여러 후보를 다 눌러 보고 그중 하나만 「적용」하면 된다.
기준 인스턴스는 지금 선택한 한 대(vCPU·스레드 상한)이고, 유입은 저장된 값으로 **정상 부하**를 가정한다 —
스파이크 같은 시간 변화는 빼야 행끼리 같은 조건에서 비교된다.
유입이 용량 한계(ρ≈1) 근처면 미리보기 값이 크게 흔들리는데, 그 흔들림 자체가 "여유가 없다"는 신호다.

### 오른쪽 — 추천

**어떤 모델을 얼마에.** 그 한 줄이 결론이다.

```
c6i.xlarge   4 vCPU · 8GB                    $140/월
```

고르는 규칙은 하나 — **목표(p95·실패)를 만족하는 것 중 가장 싼 것**.
왜 그것인지(자원 이용률·여유·더 싼 것의 탈락 이유)는 위 **인스턴스 비교** 리스트와 **병목 판정**이 이미 들고 있으므로
여기서 되풀이하지 않는다. 버스터블에 기대고 있으면 `버스트 의존` 배지만 붙인다.

목표를 만족하는 것이 하나도 없으면 빨간 머리로 **「버티는 인스턴스가 없다」**만 뜬다.

### 색 규칙

- **비교 차트에서 색은 한 번에 하나만.** 기본은 전부 **검정**이고, **고른 인스턴스만 색**으로 앞에 나온다.
  선이 저마다 제 색을 주장하면 "지금 무엇을 보고 있는지"가 흐려진다. 리스트에서 행을 누르면 색이 그쪽으로 옮겨간다
  (요청 흐름도와 차트가 한꺼번에 따라온다).
- 나머지도 **회색 농담 + 파랑 하나**. **주황**은 75% 초과, **빨강**은 90% 초과·한계 이탈에만 쓴다.
- 표에서는 나쁜 칸일수록 배경 막대가 길고 붉다. 숫자를 읽기 전에 어디가 문제인지 보인다.

## 4. 구성

브라우저만 있으면 된다. 백엔드도 빌드 도구도 없이 정적 파일 4개가 전부다.

```
index.html    화면 구조 + 스타일
engine.js     시뮬레이션 엔진(큐→스레드→커넥션→vCPU) · 병목 판정 · 요청 흐름도 · 비교 차트
advisor.js    EC2 카탈로그 → 서버 능력 환산 · 인스턴스 비교 리스트 · 추천 · 실측 보정 · 리포트
app.js        UI 바인딩 · 메인 루프(인스턴스마다 시뮬 한 벌) · 데이터 로딩 · 리스트 탭 · 설정 시나리오 표
```

## 5. 가정과 한계

- vCPU 당 성능은 세대·패밀리와 무관하게 같다고 본다 (실제로는 c 계열이 더 빠르다).
- 메모리는 스레드 상한으로만 반영한다 (스레드당 8MB, OS·런타임 40% 예약).
- 버스터블(t 계열)은 기준 이용률을 선으로만 표시하고 크레딧 소진은 시뮬레이션하지 않는다.
- DB 는 모든 인스턴스가 공유하는 같은 조건으로 둔다 (RDS 사이징·IOPS·복제 미반영).
- 네트워크·EBS 대역폭, 오토스케일링은 고려하지 않는다.
- 보정 파라미터는 측정에 쓴 로컬 검증 서버에 대한 값이다.
