# ReinforceBean 시나리오 파일 형식 v1

시뮬레이터에 트래픽을 주입하는 JSON 파일 형식이다. 두 가지 모드가 있다.

- `curve`: 시간에 따른 RPS 곡선을 키프레임으로 적는다. 엔진은 그 RPS를 평균으로 포아송 도착을 만든다. 직접 설계한 가상 시나리오용.
- `trace`: 요청 하나하나의 도착 시각을 적는다. 엔진은 적힌 시각에 정확히 요청을 넣는다. 실제 로그 재생용.

시간은 모든 곳에서 **밀리초 정수**이고, 필드 이름에 `_ms`를 붙인다. RPS 값만 초당 단위다.

## 1. 공통 필드

| 필드 | 필수 | 타입 | 설명 |
|---|---|---|---|
| `format` | O | string | 반드시 `"reinforcebean-scenario"` |
| `version` | O | number | `1`만 지원 |
| `mode` | O | string | `"curve"` 또는 `"trace"` |
| `name` | O | string | 화면에 표시할 이름 |
| `description` | - | string | 설명 |
| `duration_ms` | O | integer > 0 | 시나리오 길이 |
| `loop` | - | boolean | 기본 `false`. `true`면 `duration_ms` 주기로 반복 |
| `source` | - | object | 출처 정보. `type`(`supabase`, `handmade`, `generated` 등), `start_utc`(ISO 8601 UTC), `truncated`, `synthetic` 등. 엔진은 표시만 하고 동작에 쓰지 않음 |
| `params` | - | object | MODEL 기준값 덮어쓰기 (기존 SCENARIOS의 `params`와 같은 의미). 키는 MODEL에 존재해야 함 |
| `explain` | - | array | `{ "t_ms": integer, "text": string }` 목록. 기존 explain과 같은 용도. `text`에 `<b>`만 허용 |

## 2. curve 모드

```json
"tracks": {
  "rps": [ { "t_ms": 0, "v": 0 }, { "t_ms": 40000, "v": 100 }, ... ],
  "dbScale": [ ... ]
}
```

- `tracks.rps`는 필수. 다른 트랙 키는 MODEL에 존재하는 키만 허용한다.
- 각 점: `t_ms`는 0 이상 정수, `v`는 0 이상 유한한 숫자.
- `t_ms`는 오름차순. 같은 `t_ms`는 최대 2개까지 허용한다.
- 마지막 `t_ms`는 `duration_ms` 이하.

### 보간 규칙

시각 `x`(ms)에서 트랙 값은 다음과 같다.

1. `loop`가 `true`면 `x = x mod duration_ms`로 바꾼다.
2. `loop`가 `false`이고 `x >= duration_ms`이면, `rps`는 0, 다른 트랙은 값을 반환하지 않는다(MODEL 기본값 유지).
3. 첫 점보다 앞이면 첫 점의 값, 마지막 점 이후면 마지막 점의 값.
4. 그 외에는 `p[i].t_ms <= x < p[i+1].t_ms`인 구간에서 선형 보간한다.
5. 같은 `t_ms`가 연속 두 개면 그 시각에 순간 점프한다. 정확히 그 시각에서는 **뒤쪽 점의 값**을 쓴다.
6. 값이 같은 두 점 사이는 평평하게 유지된다.

## 3. trace 모드

```json
"events": [
  { "t_ms": 0,     "op": "read",  "ep": "GET participants", "g": 17, "src": "user" },
  { "t_ms": 57012, "op": "write", "ep": "PATCH matches",               "src": "cron" }
]
```

| 필드 | 필수 | 타입 | 설명 |
|---|---|---|---|
| `t_ms` | O | integer | 시작 기준 도착 시각. 0 이상, `duration_ms` 미만 |
| `op` | O | string | `"read"`, `"search"`, `"write"` 중 하나. 엔진의 작업 유형(조회/검색/쓰기)에 대응 |
| `ep` | - | string | 엔드포인트 이름. 표시·통계용 |
| `g` | - | integer | 묶음 번호. 한 번의 페이지 로드처럼 함께 발생한 요청들. 배율 적용 단위 |
| `src` | - | string | 출처. 기본 `"user"`. `"cron"`, `"admin"`, `"infra"` 등은 배율에서 제외 대상 |

- `events`는 `t_ms` 오름차순이어야 한다. 정렬되어 있지 않으면 불러올 때 정렬하고 경고를 표시한다.
- 같은 `t_ms`에 여러 이벤트가 있을 수 있다.

## 4. 배율 (불러올 때 적용하는 옵션, 파일에는 저장하지 않음)

파일에는 원본 규모를 그대로 두고, 배율은 실행 시 옵션으로 적용한다.

### curve 모드

`rps` 트랙의 모든 `v`에 배율 N을 곱한다. 다른 트랙과 explain은 바꾸지 않는다.

### trace 모드

입력: 이벤트 목록, 배율 `N`(> 0), 흩뜨림 범위 `jitter_ms`(≥ 0), 시드 `seed`(정수), 제외 출처 목록 `exclude_src`(기본 `["cron", "admin", "infra"]`).

1. `src`가 `exclude_src`에 있는 이벤트는 배율과 관계없이 원래 시각에 한 번만 남긴다.
2. 나머지 이벤트를 묶음으로 나눈다. `g`가 있으면 같은 `g`끼리, 없으면 이벤트 하나가 한 묶음이다. 묶음은 처음 등장한 순서로 처리한다.
3. 난수는 `seed`로 초기화한 결정적 생성기(예: mulberry32)를 쓴다. 같은 입력과 같은 시드면 항상 같은 결과가 나와야 한다.
4. 묶음마다 복제 수 `c = floor(N) + (rng() < N - floor(N) ? 1 : 0)`를 정한다. N < 1이면 묶음을 확률 N으로 남기는 것과 같다.
5. 첫 번째 복제본(k = 0)은 시각을 옮기지 않는다. 그래서 N = 1이면 원본과 완전히 같다.
6. k ≥ 1인 복제본은 `shift = round((rng() * 2 - 1) * jitter_ms)`를 뽑아 **묶음 안의 모든 이벤트에 같은 shift를 더한다.** 묶음 내부 간격은 유지된다.
7. 새 시각이 범위를 벗어나면 `((t + shift) mod duration_ms + duration_ms) mod duration_ms`로 감는다.
8. 복제본의 묶음 번호는 원본과 구분되게 새로 붙인다.
9. 전체를 `t_ms` 기준으로 안정 정렬한다.

`jitter_ms`의 의미: 작으면(예: 500) 사용자들이 같은 순간에 함께 움직이는 상황(푸시 알림, 오픈 직후)이라 피크도 거의 N배가 된다. 크면(예: 30000) 서로 독립적인 사용자라 트래픽이 평탄해진다. 둘을 모두 돌려 상한과 하한으로 비교하는 용도다.

## 5. 검증 오류 (한국어 메시지, 실패 시 이전 시나리오 유지)

- JSON 파싱 실패, 빈 파일
- `format`, `version`, `mode`, `name`, `duration_ms` 누락 또는 타입 오류
- `t`처럼 단위 없는 시간 필드 사용 시: "`t_ms`(밀리초)를 사용하세요" 안내
- curve: `tracks.rps` 누락, 점의 `t_ms`·`v` 오류, 역순, 같은 `t_ms` 3개 이상, 마지막 `t_ms > duration_ms`
- trace: `events` 누락 또는 빈 배열, `t_ms` 범위 오류, `op`가 허용값이 아님
- MODEL에 없는 `tracks` 키나 `params` 키 (문제 키 이름을 메시지에 포함)

## 6. 예제 파일과 기대 결과

### `scenarios/spike_then_surge_3min.json` (curve)

| 시각 x (ms) | 배율 1 | 배율 2 |
|---|---|---|
| 20000 | 50 | 100 |
| 59999 | 100 | 200 |
| 60000 | 400 | 800 |
| 69999 | 400 | 800 |
| 70000 | 100 | 200 |
| 125000 | 350 | 700 |
| 130000 | 600 | 1200 |
| 155000 | 350 | 700 |
| 180000 (`loop: false`) | 0 | 0 |

(59999, 69999는 선형 보간이라 소수점 이하 오차 허용. 소수 둘째 자리 반올림 기준으로 비교.)

### `scenarios/test_trace_small.json` (trace)

사용자 묶음 2개(g1: 3건, g2: 2건)와 크론 1건, 총 6건.

- 배율 1: 원본 6건과 완전히 같다.
- 배율 3, `jitter_ms` 0: 16건. `t_ms`별 개수는 1000·1005·1010·5000·5020이 각 3건, 7000이 1건.
- 배율 3, `jitter_ms` 2000, 같은 시드: 16건. 7000(크론)은 정확히 1건이고 시각이 그대로다. g1의 각 복제본 내부 간격은 5ms, 5ms 그대로다(감기로 경계를 넘은 경우 제외). 같은 시드로 두 번 돌리면 결과가 같다.
- 배율 0.5: 결과 건수는 1, 3, 4, 6 중 하나. 같은 시드면 항상 같다.

### `scenarios/vote_site_2026-09-14.json` (trace, 실측)

Supabase 로그에서 서버(node) 요청 886건을 변환한 파일. 묶음 211개, 길이 686951ms, 조회 811건, 쓰기 75건. 배율 1로 재생하면 약 687초 동안 886건이 들어와야 한다.
